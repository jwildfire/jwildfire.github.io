The Rho Graphics Group

A handful of webpages beats a 200-page PDF

Source: diary #3. The "wall of numbers" in a clinical study report was "100% impenetrable" (the post uses a Harry Potter GIF for the feeling). The Graphics Group at Rho shipped open-source tools in R and JavaScript: ggplot, D3 renderers wrapped as htmlwidgets, hosted in Shiny. The AE Explorer was inspired by Frank Harrell's Hmisc.

Headline paraphrases the post: "a handful of webpages is more useful and usable than a 200-page PDF."

The clinicians did not want a business-intelligence suite; they wanted "a guided clinical monitoring workflow supported by simple tools in their web browser."

gsm · Good Statistical Monitoring

Monitoring a trial, as software

Sources: diary #1 ("We use the {gsm} tools to monitor actual studies. We wrote a paper and have given a bunch of presentations") and diary #4 ("Unlike {safetyGraphics}, {gsm} was designed for GxP from the start").

What it is: a family of open-source R packages for risk-based quality monitoring: key risk indicators and quality tolerance limits by site, reported as HTML. gsm.core is the analytics engine; workr runs the workflows; qcthat produces the quality-control evidence. The team leads the PHUSE OpenRBQM working group.

Image: the report screenshot from the public gsm.kri README (example study AA-AA-000-0000, not real data). Jeremy to confirm it is the picture he wants, or supply a newer one.

AI in the loop

“We use AI heavily, but it's not autonomous. Humans own the process and all deliverables.”
— developer diary #1, 10 June 2026
Source: diary #1. The team "uses agentic AI, mostly via GitHub Copilot, to create open-source R packages for GxP processes related to risk-based quality monitoring." Adoption timeline from the same post: capabilities jumped in late 2025; the team started adopting agentic AI in January 2026 ("Everyone should be experimenting with this as part of your job, just to see what works") and formalised it in the following months ("Everyone should be using this every day. Who knows how skills work?").

"Humans still own every step of the process: product management, design, coding, code review, qualification, and everything else. But we use AI as a power tool throughout."

Where we put the effort

Plan → build → run: we invest at both ends

1
PlanRequirements, designs and phase gatesour scaffold
2
BuildVendor coding agents, plus our shared context and conventionsmaintained
3
RunStudy set-up, snapshot schedules, checks against the monitoring planour scaffold
Source: the team's Q3 2026 agentic update deck (internal), strategy slide. The headline there: "we moved focus from coding agents to the roadmap and operations scaffolds, where the value was." The chain follows the product lifecycle: the roadmap produces the specs and sub-issues that coding consumes; coding produces releases that operations deploys to studies.

Why both ends: they are company-specific process that no vendor will build. The middle is commodity and improving monthly.

Vet before publishing: everything on slides 15–20 comes from that internal deck.

Title is Jeremy's line (2026-10-02). Source: Q3 deck, "Coding: maintained, not abandoned": "Vendor coding agents improve monthly, so we invest in shared context, not a custom agent." gsm.agent is one AGENTS.md (the map of the gsm repos plus conventions: attribution, test-first development, worktrees) and three skills; unchanged since July, by design. A deeper issue-to-pull-request pilot and domain skills are parked until 2027.

How we build the scaffolds

Deterministic tools first, agents on top

1
FrameworkGitHub as the system of record: issues, a lifecycle, decision recordsreliable
2
ToolsScripts and Actions that compute the evidencereliable
3
SkillsVersion-controlled procedures an agent loads for a taskreliable
4
BotsAgents acting on a schedule, under their own identitystill learning
Source: Q3 deck, "Framework → Tools → Skills → Bots". "Each layer only works once the one below it is solid. Layers 1–3 are reliable today; layer 4 is where we're still learning."

The line worth saying out loud: "Deterministic tools come before agents on purpose: agents write prose on top of evidence the tools compute, so the numbers stay right even when an agent fails."

Example for the stage: the weekly check of each study's configuration against its monitoring plan runs with no model at all. An agent wrote the checker and its matching rules; the rules stay marked "inferred" until an engineer confirms them.

Echo for beat 3: the obot summer learned the same thing the hard way ("never let an agent be the sole watcher of an agent", diary #8). Cut candidate if beat 2 runs long.

Source: Q3 deck, roadmap scaffold slides, and the gsm.roadmap README. Every requirement moves through the same six stages; a person records sign-off at each gate and the stage only advances when the gate's evidence passes. Agents draft most of the written artifacts (requirements, specs, designs, implementation plans) from templates, through 13 skills; each artifact is published by a validated pull request and indexed on the roadmap site.

Numbers available if wanted on the slide (late September): 13 skills, up from 7 in July; 82 requirements tracked; 64 artifacts across 29 requirements; 103 linked sub-issues across 17 repos; 132 pull requests merged since early July; 23 architecture decision records.

The abstract's wording: "{gsm.roadmap} decomposes requirements with AI-assisted planning using GitHub workflows." Ties forward to beat 4: requirements before work.

Run · operations

One repo per study, one hub to run them

  • Study repos — 20 studies, each with its own configuration and snapshot workflow
  • Central scheduling — one schedule opens issues in every study repo; the dashboard updates daily
  • Intake and a guide — request forms, and a 15-step study set-up guide
  • Plan alignment — a weekly check of each study's configuration against its monitoring plan
Jeremy's steer (2026-10-02): "One repo per study, central repo for monitoring." Source: Q3 deck, "The operations scaffold at a glance".

Production workflows run under a bot identity. The plan-alignment check is fully deterministic at runtime; an agent drafted the code and the matching rules.

Run · what changed

The hub replaced spreadsheets and email

Before

Schedules in several Excel trackers
Status chased by email
No live view for leadership

Now

Merge a schedule, and issues open in each study repo
A live dashboard, updated daily
A full audit trail through pull requests

Source: Q3 deck, "The Central Monitoring hub replaced spreadsheets and email". Also on that slide: self-serve editors with approver sign-off; cadence growing toward weekly; 20 study repos managed and 19 production workflows.

Results are qualitative so far: clinical leadership owns the schedule editor, the email chains are gone, nobody compiles status by hand.

The talk's point: this is where agentic engineering paid off at work. Not faster code, but operations moved into version control, with an audit trail as a side effect.

The rule that doesn't change

AI-written code still needs a human owner

  • A person owns the requirements.
  • A person owns the risk decision.
  • A person must be able to explain why the code works.
  • A person must be able to explain why it is safe enough for medical research.
The four lines are verbatim from the 6 June deck draft (RPharma2026-AIKeynote), which came from Jeremy's dictation. Same idea in the abstract: scaffolding that keeps AI behaviour "repeatable, auditable, and governed by the humans who remain responsible for every line of code."

Old deck's guardrail grid, if a second slide is wanted: Evidence, Permissions, Traceability, Humans.

The bridge

Open, software-shaped workflows are agent-ready.
So what happens when the agent does more of the work?
Hand-off into beat 3. The claim is from the 6 June deck ("Once the workflow is open and software-shaped… AI can do more than autocomplete code") and the dictation notes ("Agentic AI is arriving into that context, not replacing it from scratch").

The honest set-up for the experiment, from diary #1: "I'm not comfortable using those highly autonomous tools for GxP use cases right now, but the capabilities are coming, and I want to understand them." So the experiment runs on something that is not GxP yet: safetyGraphics.
